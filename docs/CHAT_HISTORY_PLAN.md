# 第二步：会话持久化

## 目标和分工

在现有 MySQL 中保存聊天记录；登录同一账号后能查看旧会话、继续对话。
后端负责读取历史和校验归属，前端不再上传完整历史。

用户亲手编写模型、归属校验、上下文组装和消息保存逻辑；Codex 提供代码讲解、审查和验证，并直接实现前端改动。

## 第一版范围

- 会话列表、新建会话、查看消息、继续聊天、删除会话。
- 保留当前 SSE 流式回复和当前页面内的预约确认卡片。
- 历史会话先恢复文本，不恢复预约卡片和工具执行过程。
- 不引入 checkpointer、新数据库或 LLM 标题生成。
- 暂不添加没有实际用途的 draft_id 字段。卡片恢复后续单独设计，需要考虑一条消息对应多个确认单、凭证恢复和幂等键。

## 数据模型

沿用 Base 的 id、create_time、update_time。

| 表 | 新增字段 | 说明 |
| --- | --- | --- |
| conversations | user_id、title | user_id 外键指向 users.id，并建索引；标题最长 100 字符 |
| chat_messages | conversation_id、role、content | conversation_id 外键指向 conversations.id，并建索引；role 只由服务端设置为 user 或 assistant；正文用 Text |

首条用户输入截取前 30 字符作为标题。每次保存消息时显式更新会话的 update_time，不能指望插入子表自动触发父表更新时间。
先使用普通外键，不增加 ORM 双向关系。删除时先删消息，再删会话，同一事务提交，失败一起回滚。

## 接口契约

| 方法和路径 | 用途 |
| --- | --- |
| GET /api/ai/conversations | 分页查询当前用户的会话，默认 page=1、page_size=20，page_size 最大 100 |
| GET /api/ai/conversations/{id}/messages | 分页读取消息，按 id 倒序选取一页后正序展示；默认每页 50 条，最大 100 |
| DELETE /api/ai/conversations/{id} | 删除当前用户的会话和消息 |
| POST /api/ai/chat/stream | 新建或继续会话，输入 conversation_id 和 message |

聊天请求示例：

```json
{
  "conversation_id": null,
  "message": "明天有哪些开放的实验室？"
}
```

conversation_id 为空时由服务端创建会话；否则先按会话 ID 和 JWT 用户 ID 查询归属。
message 去除首尾空白后长度为 1～2000 字符；conversation_id 提供时必须为正整数。
请求模型启用 extra="forbid"，旧 messages 字段返回 422。前后端一起切换契约。

所有涉及指定会话的接口，查询均包含当前用户 ID，不存在或不属于本人统一返回实际 HTTP 404。
聊天归属和输入校验在创建 StreamingResponse 前完成，避免只能通过 SSE 发送权限错误。

## 一轮聊天的顺序

1. 校验身份、输入和会话归属；必要时创建会话。
2. 保存本次用户消息并更新会话时间，提交短事务。
3. 从数据库查询最近 20 条 user/assistant 消息，按 id 正序组成上下文；本次用户消息已经在其中，不能重复追加。
4. SSE 第一条事件返回 conversation_id，前端立即记录它。
5. 运行 Agent，保持现有 status、tool_start、tool_end、reservation_draft、token 等事件。
6. 内存中累积助手文本；正常结束时保存完整回复并更新会话时间，提交成功后才发送 done。
7. 失败时回滚当前写入、发送明确错误；已保存的用户消息保留，未完成的助手正文不落库，也不进入下轮上下文。

不要逐 token 写数据库，也不要持有写事务等待模型完成。数据库提交失败不能向前端报告已保存成功。
最近 20 条是消息数量限制，不是严格的 token 预算。当前轮的工具调用仍由 LangGraph 管理，不把历史工具调用片段混入重建的上下文。
连接取消不能保证还能发送 error；实现时需显式处理取消、关闭会话资源，旧页面上的部分回复在刷新后可能消失。

## 前端改动

- 增加会话列表、新建、选择和删除操作。
- 发送时只传 conversation_id 和本次 message，不再拼完整历史。
- 收到 conversation 事件后记录服务端返回的会话 ID，并刷新列表。
- 打开旧会话加载消息，支持加载更早记录。
- 首次进入加载最近会话；欢迎语作为页面提示，不写入数据库。
- 单轮生成期间禁用重复发送及会话切换、删除，避免回复写入错误的页面。
- 跨标签页对同一会话同时发送/删除的处理，在流式改造时单独验证并确定服务端方案；前端禁用按钮不能代替服务端控制。
- 历史页明确提示暂不恢复确认卡片；预约结果以预约记录为准。

## 编写顺序

1. 用户编写两个模型，注册到 main.py 的 create_all 之前；审查后启动验证。
2. 用户编写会话列表、消息列表、删除的 service 和 API，先验证归属和事务。
3. 用户新增 ConversationChatRequest、修改上下文组装和流式落库顺序，验证错误与取消路径。
4. Codex 修改前端、更新受影响的测试，完成联调。

## 验收

- 同账号换浏览器仍能看到旧会话，继续聊天能引用历史。
- A 账号无法读取、续聊或删除 B 的会话，返回 HTTP 404，不新增任何消息。
- 旧 messages 入参及额外字段被 422 拒绝；空白输入、超长输入被拒绝。
- 超过 25 条消息后，模型历史仅取最近 20 条且顺序正确；数据库保留完整文本记录。
- 模型失败、数据库写入失败、连接取消不会把未完成回复当作正常历史。
- 删除会话不留孤立消息；重复加载页面不创建新会话或重复消息。
- 当前页面的确认/取消预约仍正常；历史卡片暂不恢复的限制清楚可见。

当前仅在一个页面内阻止重复发送及生成时切换、删除会话。多个标签页或客户端仍可能同时续聊/删除同一个会话，服务端互斥尚未实现，因此这部分验收仍未完成。
